  3. 03
    • TypeScript
    • LLM prompting
    • Slack API
    • GitHub Actions

    AI pipeline for developer pain points

    Built a daily-to-monthly pipeline that reads our developer support channel and tells platform leads which parts of the platform actually hurt — classified by area, counted weekly, summarized monthly. About 1,000 messages a week, 50,000+ since it went live.

    How it works

    A daily action pulls the last 24 hours of support messages and filters the noise — bot posts, join events, and one-word replies that carry no signal.

    A weekly action classifies what's left. Each message goes through a regex keyword pass built from vocabulary I collected from the leads of each platform area, then to an LLM with that context attached and prompting tuned to return exactly one category token. Counts per area go to Slack every week.

    A monthly action pools a month of classified messages by area and asks for ranked pain points with suggested remediations, grounded only in the messages themselves — no outside speculation. That summary goes to managers and team leads.

    Before any of it, I ran a spike comparing three storage backends — vector search, expiring CI artifacts, and a durable artifact repository — and wrote up the tradeoffs. Vector search can't reliably answer "everything from last week," and expiring artifacts make past classifications impossible to audit, so durable storage won.

    Designed and built the system that provisions custom Kubernetes namespaces on demand — now 143 namespace definitions across 13 EKS clusters. Teams used to get exactly one namespace per cluster, tied to the team name — a second one meant inventing a second team.

  7. 07
    • TypeScript
    • GitHub API
    • GitHub Actions
    • OIDC

    Team-aware pull request approval gate

    Built the merge gate that decides whether a pull request has actually satisfied its review requirements, publishes that decision as a commit status, and keeps a live approval table in the PR body. Solo, from an empty repository.

    How it works

    Counting approvals sounds trivial and isn't. Almost all the work was writing down a policy for the cases most approval scripts get wrong, and then holding to it:

    • Comments don't revoke — leaving a comment after approving used to silently withdraw the approval. Requesting changes revokes; commenting doesn't.
    • Multi-team quorum — each required team can be made to reach the threshold independently, or approvals can pool across teams with a reviewer on two teams counted once.
    • Small teams can't deadlock — if a required team has fewer members than the threshold, fallback reviewers are added to it rather than swapped in for it.
    • Bots and the author never count — no self-approval, no inflating quorum with automation.
    • Missing approvals aren't failures — the gate reports pending and only fails on a genuine execution error, so a red check always means something is actually broken.

    It authenticates through OIDC to a short-lived app token rather than a long-lived personal token, which matters more than usual for something that runs on every pull request.

  8. 08
    • TypeScript
    • OIDC
    • GitHub API
    • OpenAI API

    Declarative identity lifecycle automation

    Automated joiner-mover-leaver across a 3,295-member GitHub Enterprise and our OpenAI Platform accounts. Membership is declared in config; the system works out the difference and applies it.

    How it works

    This is the piece of work I'd defend hardest on design. It is a level-triggered reconciler in the Terraform sense: a pure plan function reads desired state and observed state and returns the set of changes, and a separate apply step is the only thing allowed to mutate anything. Planning has no side effects, so it is cheap to test — you assert on a diff, not on a mock of a vendor API.

    • Dry run first — every destructive path supports, and defaults to showing, the plan before it runs. Revoking someone's access by accident is not a bug you get to fix afterwards.
    • Two identities, one person — dormant accounts are only reaped when the GitHub username and the corporate directory email agree, because either signal alone produces false positives.
    • No long-lived secrets — jobs authenticate through OIDC and fetch credentials at runtime, so there is nothing standing in a repository to leak.
    • A typed client — I wrote the typed wrapper for the OpenAI administration API rather than passing untyped JSON around the reconciler.
